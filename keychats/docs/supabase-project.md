## Sole admin bootstrap

The fixed Keychats admin login ID is `cxu1344`. `npm run bootstrap:admin` creates or updates only that account and sets authorization in `app_metadata.role = 'admin'`.

The script refuses to start unless `NEXT_PUBLIC_SUPABASE_URL` is exactly the Keychats project URL. This is an additional guard against accidentally provisioning Auth/profile data into PlanDoSee.

Run it only with runtime environment values, for example from a trusted local shell or protected deployment environment. Do not put the actual admin password in a committed `.env` file, workflow YAML, command history shared with others, or chat transcript.

Bootstrap also creates/updates the admin profile and settings and ensures membership in `#general`. It marks that room as the default channel and does not print the password.

## Applied hosted migrations

The hosted Keychats project currently includes:

- core schema
- RLS policies
- advisor indexes
- atomic invite claim/finalize/release state
- channel constraints for the default room and normalized channel names
- message moderation and message Postgres Changes publication
- message reaction, pin, and read-state Postgres Changes publication
- secure private storage for avatars and chat attachments, including attachment Realtime publication

The channel-constraint migration adds `channels.is_default`, enforces case-insensitive/trimmed channel-name uniqueness, marks `#general` as the default room, prevents ordinary users from creating another `general` room, and prevents even the administrator from deleting the default `#general` channel.

The hosted `secure_storage` migration creates private `avatars` and `chat-attachments` buckets, enforces the 10 MiB limit and allowed MIME types, adds Storage RLS, restricts attachment metadata to the sender's own live message, and publishes attachment metadata changes for Realtime refresh.

Invite contract:

- a newly created invite is valid for exactly **1 hour**
- the raw invite token is returned only when the invite is created; the database stores its SHA-256 hash
- only one successful registration may consume an invite
- revoked, expired, or already-used invites cannot be claimed
- completing registration does **not** create an account expiry; the account remains usable until an administrator disables or expels it
- privileged invite RPCs are server-only: `anon` and `authenticated` have no execute permission, while the server secret/service role can call the public server wrappers

## Local development

`keychats/supabase/config.toml` is generated by the current Supabase CLI via `supabase init` and is used only for the local development stack. Remote schema changes must be represented by migrations in `keychats/supabase/migrations/` before merge.
